# 从零微调一个中文金融小模型（4GB 显卡实操）

这篇教程按我实际做过的顺序写：环境 → 数据 → 小样跑通 → 全量训练 → 评估 → 封成 agent。每一步都有命令和"该看到什么"，出问题时有对照表。

结论先给你：**Qwen3-0.6B + LoRA，4GB 显存，单任务 2~3 小时，情绪 75.2% / 新闻 89.7% / 主体抽取 86.1%。**

---

## 0. 先算显存账，决定你能不能跑

微调的显存大致由三块组成：模型权重、梯度与优化器状态、激活值。

| 方法 | 0.6B 模型粗算 | 我们实测 |
|---|---|---|
| 全参微调（fp16 + Adam） | 权重 1.2G + 梯度 1.2G + 优化器 4.8G + 激活 ≈ 8G 起 | 跑不了 |
| LoRA（只训 adapter） | 权重 1.2G + adapter 0.01G + 优化器极少 + 激活 | **1.55G** |
| LoRA + 梯度检查点 | 激活再降一半 | 1.55G（就是这档） |

所以 4GB 卡的正确姿势是：**LoRA + 梯度检查点 + 小 batch + 梯度累积**，不要碰全参。

再补一个容易忽略的点：`lm_head` 的输出是 `序列长度 × 词表大小`。序列 512、词表 15 万、fp16 就是 150MB，一叠加就爆。我们后来改成"只对答案位置算 logits"，直接省下约 600MB，这一步是 4GB 卡能跑起来的关键。

## 1. 环境部署

### 1.1 Python 与虚拟环境

用 Python 3.11。虚拟环境随便（venv / conda / uv），只要别装到系统 Python 里。

```bash
python -m venv venv
# Windows
venv\Scripts\activate
# Linux / macOS
source venv/bin/activate
```

### 1.2 装 PyTorch（最容易踩坑的一步）

**CUDA 版本要和显卡驱动匹配**，不是越新越好。先看驱动：

```bash
nvidia-smi        # 右上角 "CUDA Version: xx.x" 是驱动支持的上限
```

老卡老驱动（比如 GTX 1650 + 457.49 驱动）最高只能用 cu118：

```bash
pip install torch==2.7.1 --index-url https://download.pytorch.org/whl/cu118
```

装完必须验证，别急着往下走：

```bash
python -c "
import torch
print('cuda 可用:', torch.cuda.is_available())
print('显卡:', torch.cuda.get_device_name(0))
print('算力:', torch.cuda.get_device_capability(0))
print('显存: %.1f GB' % (torch.cuda.get_device_properties(0).total_memory/1024**3))
"
```

看到 `cuda 可用: True` 才算过。`False` 的三种常见原因：装成了 CPU 版、CUDA 版本高于驱动、驱动本身没装好。

**算力那一行很重要**：GTX 1650 是 `(7, 5)`，属于 Turing。Turing 上 `bfloat16` 支持很差，训练必须用 `float16`，否则要么报错要么慢得离谱。

### 1.3 装依赖

```bash
pip install transformers==5.21.0 peft==0.21.2 safetensors numpy tqdm
```

版本不一定要和我一样，但 `transformers` 和 `peft` 尽量成对升级，混用容易出奇怪的 API 报错。

## 3. 准备数据

### 3.1 格式

统一用 alpaca 三字段，一条一行 JSON 或一个 JSON 数组：

```json
{
  "instruction": "判断以下句子的情感属性。",
  "input": "该公司一季度净利润同比增长三成。",
  "output": "积极"
}
```

### 3.2 我们的三份数据

| 任务 | 训练 | 评估 | 来源 |
|---|---|---|---|
| 情绪三分类 | 16,157 | 2,020 | FinCUGE 的 FinFE |
| 新闻七分类 | 7,071 | 884 | FinCUGE 的 FinNL（15 类并成 7 类） |
| 事件主体抽取 | 11,752 | 1,464 | FinCUGE 的 FinESE |

转换脚本：`prepare_fincuge.py`（原始数据 → alpaca）、`prepare_newscat7.py`（15 类 → 7 类）。

### 3.3 训练前必须看数据

```bash
python check_train.py      # 掩码、补零、切分、梯度自检
python check_entity.py     # 实体任务专用：判分器能不能抽出实体、实体是否在原文
```

这两个脚本会告诉你三件要命的事：

1. **标签合法性**：分类任务的答案能不能解析出唯一标签
2. **答案长度**：决定 `max_new_tokens` 和序列长度，实体任务实测 P99 只有 18 token
3. **答案是否在原文里**：实体任务里 99.98% 在原文（模型可以照抄），不在原文的那几条就是准确率天花板

## 4. 第一次训练：先用 30 条跑通

**不要一上来跑全量。** 30 条、1 轮、几分钟就能验证整条链路：

```bash
python train_sft.py --data_path data/fincuge/emotion_train.json --num_samples 30 \
  --seq_len 128 --batch_size 2 --grad_accum 1 --epochs 1 --fast_loss 1 \
  --out out/smoke
```

该看到的东西，逐条对：

| 该看到 | 说明 |
|---|---|
| `trainable params: 5,046,272 / 601,096,192 = 0.8395%` | adapter 挂上了 |
| `[自检] 拿到梯度的参数 392/392` | 梯度真的回传了，不是白训 |
| `loss` 从 2.x 开始往下走 | 只要在动就算通 |
| `峰值显存 1.5x G` | 没爆 |
| 结束时 `out/smoke` 有 `adapter_model.safetensors` | 存盘正常 |

这一步不过，后面全量训练都是白烧电。

## 5. 全量训练

### 5.1 三条命令

```bash
# 情绪三分类
python train_sft.py --data_path data/fincuge/emotion_train.json --num_samples 16157 \
  --seq_len 128 --batch_size 2 --grad_accum 4 --epochs 1 --fast_loss 1 \
  --out out/adapter-emotion

# 新闻七分类
python train_sft.py --data_path data/fincuge/newscat7_train.json --num_samples 7071 \
  --seq_len 512 --batch_size 2 --grad_accum 4 --epochs 1 --fast_loss 1 \
  --out out/adapter-newscat

# 事件主体抽取
python train_sft.py --data_path data/fincuge/entity_train.json --num_samples 11752 \
  --seq_len 320 --batch_size 2 --grad_accum 4 --epochs 1 --fast_loss 1 \
  --out out/adapter-entity --val_metric entity --val_limit 200
```

### 5.2 参数逐条解释

| 参数 | 我们的取值 | 为什么 |
|---|---|---|
| `seq_len` | 128 / 512 / 320 | 按数据 token 长度 P99 定。情绪和实体短（实体 P99=201），新闻长所以 512 |
| `batch_size` | 2 | 显存上限，没得选 |
| `grad_accum` | 4 | 等效 batch 8，弥补小 batch 的噪声 |
| `epochs` | 1 | 这套数据单轮就收敛，多轮开始过拟合 |
| `lr` | 2e-4 + cosine | LoRA 常用区间，warmup 10% |
| `fast_loss` | 1 | 只对答案 token 算 logits，省 600MB |
| `save_every` | 300 | 每 300 步存断点，断电最多丢 300 步 |

### 5.3 怎么定序列长度

别一拍脑袋写 512。先量：

```bash
python -c "
import json,sys; sys.path.insert(0,'.')
from transformers import AutoTokenizer
from prompt_util import build_user_text
tok=AutoTokenizer.from_pretrained('models/Qwen3-0.6B')
L=[len(tok.encode(build_user_text(r),add_special_tokens=False))+len(tok.encode(r['output'],add_special_tokens=False))+8
   for r in json.load(open('data/fincuge/entity_train.json',encoding='utf-8'))]
L.sort(); print('P50',L[len(L)//2],'P99',L[int(len(L)*0.99)],'max',L[-1])
"
```

我们实体任务 P50 只有 77、P99 是 201。按 512 训等于一半时间在算 padding，改成 320 省掉三分之一时间，只丢 27 条（0.23%）。

## 6. 训练中途看什么

日志每 40 步一行：

```
epoch 1/1 | step 440/1318 | loss 0.1936 | lr 1.69e-04 | 峰值显存 1.55G | 已用 67.9min | 剩 135.4min
```

看四个数：

1. **loss 的趋势**，不是绝对值（见下节）
2. **lr 是否在按 cosine 下降**（升到峰值再降下来）
3. **显存是否稳定**（一路 1.55G 就对了，忽高忽低说明有泄漏）
4. **剩余时间**（每 40 步刷新一次，用它估算什么时候能停）

## 7. 怎么判断训练是正常的

| 任务 | 正常 loss 区间 | 我们的实测 |
|---|---|---|
| 情绪三分类 | 0.2~0.4 | 2.20 → 0.24（稳定在 0.24~0.29） |
| 新闻七分类 | 0.2~0.5 | 收敛到 0.3 附近 |
| 事件主体抽取 | 0.1~0.3 | 2.20 → 0.16 |

三个判据比 loss 靠谱：

1. **验证集**：每轮末在留出集上跑一次，分类看准确率，实体看严格匹配率
2. **跟训练集对比**：验证比训练差很多 → 过拟合；两个都很差 → 学习率或数据有问题
3. **不要用 loss 判断分类好坏**：我们把答案压成只剩标签词后 loss 掉到 0.05，准确率却只涨 1.1 个点。loss 低不等于分得准

## 8. 评估

### 8.1 三种口径，别混用

| 口径 | 适用 | 做法 |
|---|---|---|
| 生成式 | 通用 | 生成答案 → 从文本里解析标签/实体 |
| 受限 softmax | 分类任务 | 一次前向，只在候选标签 token 上归一化取最大 |
| 实体匹配 | 抽取任务 | 生成 → 抽实体 → 严格全等 + 宽松包含 + P/R/F1 |

分类任务为什么推荐受限 softmax：答案可能有十几种写法（"积极。"、"该文本情感是积极的。"），生成式要额外处理格式；受限 softmax 直接读三类概率，一次前向，还顺带得到置信度。

### 8.2 命令

```bash
python eval_verbalizer.py --limit 0 --adapter out/adapter-emotion --batch 4
python eval_multi.py --task newscat7 --adapter out/adapter-newscat
python eval_entity.py --adapter out/adapter-entity
```

`--limit 0` 表示全量。**报绝对分数只能用全量 + 原始分布**：我们曾经用 120 条分层样本报 70.8%，全量实测 75.2%，差了 4.4 个点。

### 8.3 别只看总分

看错例。我们实体任务 203 条错例里，78% 是"原文有多个公司名挑错了"，22% 是"多一个字少一个字"。这两种错法的修法完全不同：前者要改任务定义或加规则，后者只要放宽匹配。

## 9. 保存、加载、续训

产出三个目录：

```
out/adapter-emotion       最后一轮的 adapter
out/adapter-emotion_best  验证集最好的那一轮
out/adapter-emotion_ckpt  中途断点
```

每个 adapter 只有两个文件：`adapter_config.json` + `adapter_model.safetensors`（约 20MB）。

加载：

```python
from transformers import AutoModelForCausalLM
from peft import PeftModel
m = AutoModelForCausalLM.from_pretrained("models/Qwen3-0.6B", dtype=torch.float16, device_map={"": "cuda:0"})
m = PeftModel.from_pretrained(m, "out/adapter-emotion")
```

续训要老实说一句：`--resume` 是**热启动**不是严格续训，只恢复权重，不恢复 Adam 的动量。写报告时别含糊。

## 10. 封成 agent

三个 adapter 可以挂在同一个基座上，由一个外壳调度：

```python
from harness import Harness

h = Harness()
h.answer("这家公司业绩暴雷，投资者情绪一片悲观")
# {'task': 'emotion', 'answer': '消极', 'confidence': 0.922, 'decision': 'auto'}
```

阈值不要拍脑袋，用 `calibrate.py` 在评估集上算：

```bash
python calibrate.py
```

它会给出每个任务"阈值 → 覆盖率 → 该档准确率"，你按自己能接受的误答率挑。我们的结果是：情绪 0.90（覆盖 37%、94.3%）、新闻 0.95（覆盖 79%、95.4%）、实体 0.89（覆盖 39%、95.1%）。

## 11. 报错对照表

| 现象 | 原因 | 处理 |
|---|---|---|
| `CUDA out of memory` 但显存看着还有 | 碎片 | 加 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，或降 batch/seq_len |
| `Tried to allocate XXX MiB` 卡在 lm_head | 全序列 logits | 用 `--fast_loss 1` |
| `bf16` 相关报错或结果全 nan | Turing 卡不支持 bf16 | 全链路用 `float16` |
| `torch.cuda.is_available() == False` | CPU 版 torch / CUDA 高于驱动 | 按驱动重装对应 cu 版本 |
| 训练 loss 一直 0 或 nan | 学习率过大 / label 全被 mask | 先跑 30 条小样，检查"被监督 token 数"大于 0 |
| 生成只有半截句子 | `max_new_tokens` 太小 | 先量答案 token 长度 P99，再定 |
| 评估准确率明显低于预期 | 训练和评估的提示词不一致 | 两边必须共用同一个拼接函数，不许各写一份 |
| 长任务跑到一半进程没了 | 被系统或终端回收 | 用 `setsid`/`nohup` 或放进 tmux，日志落盘 |
| 断点续训后 loss 突然变大 | 热启动丢动量 | 属正常，多跑几十步会回落 |

## 12. 4GB 卡能跑多大

经验值（LoRA + 梯度检查点，序列 ≤512）：

| 模型 | 能否训练 | 备注 |
|---|---|---|
| 0.5B / 0.6B | 能，1.5~2GB | 本仓库的配置 |
| 1.5B | 勉强，3~3.5GB | 要降到 batch 1、序列 256 |
| 3B | 不能 | 权重就 6GB |
| 7B | 不能 | 需要量化推理，训练别想 |

想上更大模型，正路是 QLoRA（4bit 量化）或租云卡，不是硬压参数。
