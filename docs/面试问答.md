# 面试问答准备（基于本项目 + 公开面经）

> 依据：CloudVyn《Ace Your LLM Fine-Tuning Interview Questions 2026》、TopGenAIJobs《Fine-Tuning Interview Questions》、TechInterview《What LoRA interviews test》、CloudSoftSol《55 Fine-Tuning Questions》、以及中文 LoRA 面经两篇。
> 所有答案里的数字都来自本项目实测，可以当场对账。

## 0. 一条总原则

面经里反复出现同一个评分标准：讲项目要给出**基座 + 方法 + 数据量 + 评估口径 + 一个诚实的局限**。缺任何一项都会被追问。我们的对应值是：

> Qwen3-0.6B + LoRA（r=8，7 个模块，0.84% 参数）+ 情绪 1.6 万 / 新闻 7 千 / 实体 1.2 万 + 全量评估（2,020 / 884 / 1,464）+ 局限：新闻任务类别数被我从 15 并到 7，和公开报告不可比。

## 1. 选型类（出现概率最高）

**Q1：这个任务为什么用微调，不用 RAG 或者更好的提示词？**

- 想听：你是否知道三者的边界。面经原话：RAG 解决"知识新、要引用"，微调解决"格式、语气、稳定输出"，提示词解决"能描述清楚的任务"。
- 答：三个任务都是**窄分类/抽取**，不是知识问答，RAG 帮不上。提示词试过，0.6B 零样本只有 48.3%（情绪）、26.4%（新闻）、0.5%（实体），因为小模型不会主动按固定格式输出。微调解决的是"格式 + 判别边界"，一次训练 3 小时换 20~85 个点，这是三者里性价比最高的。
- 别踩：别说"微调能注入知识"。那是 RAG 的活，也是面经里明确列为"常见错误"的一条。

**Q2：为什么选 0.6B，不用 7B 或者直接调 API？**

- 答：约束驱动。目标场景是金融内网，数据不能出网，所以 API 直接排除；7B 权重 14GB，一张 4GB 卡装不下。0.6B 是"能在 4GB 上训练 + 中文指令跟随还能用"的最大值。而且这三个任务是窄任务，实测 0.6B 微调后在两项上超过了 GPT-4o 的零样本成绩，说明瓶颈不在参数量。
- 追问陷阱："那 7B 微调是不是更好？" 答：在同样数据上大概率更好，但代价是换硬件；如果给我 24GB 卡，我会先做 7B 的对照，再决定是否值得。

**Q3：为什么不选全参微调 / QLoRA？**

- 答：全参 0.6B 大约要 8GB（权重 1.2 + 梯度 1.2 + Adam 状态 4.8 + 激活），4GB 卡放不下。QLoRA 在 Turing（sm_75）上 4bit 反量化算子不稳定、还更慢，属于"为省显存牺牲速度"，而我们省下来的显存用不上（1.55GB 已经够）。LoRA 还能随时 merge 回基座、推理零额外延迟，这三个理由都指向 LoRA。
- 加分点：说出 QLoRA 的三个机制（NF4、双重量化、paged optimizer）和一句"4bit 训练并不等于梯度在 4bit 上算，梯度仍走 bf16"。

## 2. LoRA 原理类（几乎必问）

**Q4：LoRA 的数学形式，为什么省显存？**

- 答：冻结 W₀，只学低秩增量 ΔW = B·A，前向是 h = W₀x + (α/r)·BAx。B 初始化为 0，所以训练开始时等价于原模型。省显存的关键不是权重，而是**优化器状态**：Adam 要为每个可训练参数存两个动量，全参 6 亿参数要 4.8GB，LoRA 只有 505 万参数，几乎不占。我们的实测是 5,046,272 / 601,096,192 = **0.84%**，峰值显存 1.55GB。

**Q5：r 和 alpha 怎么定的？为什么是 8 和 16？**

- 诚实答（推荐）：**这两个数我没做消融**。当时是显存优先 + 参考两个开源项目的默认值（LLaMA-Factory 用 8、Unsloth 用 16），选了 8，alpha 按惯例取 2r。如果重来，我会跑 2×2 消融（r∈{8,16} × target∈{注意力, 全部线性层}），用验证集定，而不是拍。
- 为什么这样答：面经明确写了"你说 alpha=32 是因为教程这么写，等于告诉面试官你不知道它干什么"。承认没做，比编一个理由安全。
- 补一句原理：α/r 是缩放，保持 α 与 r 成比例，改 r 时等效学习率才不会变。

**Q6：target_modules 为什么挂 7 个？**

- 答：q/k/v/o + gate/up/down。早期 LoRA 论文只挂 q/v，现在的实践挂全部线性层，因为 MLP 里存了大量"知识转换"能力，只冻注意力会限制适配上限。我们挂 7 个后参数量 505 万，仍然只占 0.84%，显存代价可接受。

**Q7：LoRA 能 merge 吗？推理要不要多一步？**

- 答：能，W = W₀ + BA，merge 后推理零额外延迟。我们没 merge，因为我们同时挂三个 adapter 做任务切换，merge 就失去热切换能力了。代价是每次请求多一次 adapter 前向，实测端到端 1 秒左右。

## 3. 数据类

**Q8：数据哪来的，多少条，怎么清洗？**

- 答：FinCUGE 的指令化版本，三个任务分别是 16,157 / 7,071 / 11,752 条训练。清洗做了四件事：①标签归一（新闻原始标签是整句话，抽出类别词）；②长尾合并（新闻 15 类里"中国""国际"各只有 2 条，并进"其它"）；③长度过滤（按 token P99 定序列长度，实体任务 P99=201）；④冲突检测（同一段文本被标不同标签的占 9.6%，这是准确率天花板）。

**Q9：标签噪声你怎么处理？**

- 答（这是加分题）：检测到了但没治理。手法是统计同一 input 的答案分布，发现 773 种文本被标了不同标签（9.6%）。已知的治理路径是置信学习（Cleanlab）：用交叉验证拿到折外概率，找出"模型很确信、标签却相反"的样本，删除或人工改正。外部证据是只删除能让误差降 8%，改正能降 37%。这是我们下一步最该做的事。

**Q10：有没有数据泄漏？**

- 答：训练/评估是原始划分，评估集没进训练。但要说清一个瑕疵：**我们所有报告的数字都在 valid 切片上，公开报告用的是 test 切片**，两者规模接近但不是同一批样本。这是个已记录的待办，不是"没发现"。

## 4. 评估类（最能区分水平）

**Q11：76.3% 是什么口径？为什么不用准确率之外的指标？**

- 答：情绪是 Accuracy + Weighted-F1，两者都报（0.7634 / 0.7542）。分类任务只报 accuracy 会掩盖类别不平衡，所以同时给三类 F1：积极 0.84 / 消极 0.78 / 中性 0.60。中性差是数据问题（标签冲突集中在中性），不是模型结构问题。

**Q12：为什么情绪用受限 softmax，而不是生成后解析？**

- 答：这份数据的答案有 15 种句式（"积极。"、"该文本情感是积极的。"…），生成式要先解析再判分，格式噪声会混进准确率。受限 softmax 只在"积极/消极/中"三个 token 上归一化，一次前向同时得到标签和置信度，还把评估速度从 450ms/条 降到 229ms/条。

**Q13：新闻 89.7% 和公开报告的 83.6% 能比吗？**

- 主动说：**不能**。公开是 15 类，我们是 7 类（长尾合并），类别少一半、长尾全进"其它"，天然容易得高分。要严格比较得把 15 类重训一遍。
- 这题的作用：面试官常在等你是否主动暴露不可比。等被问出来再解释，可信度会掉一半。

**Q14：实体 86.1% 的错在哪？**

- 答：1,464 条里错 203 条。78% 是"原文有多个公司名，挑错了"；22% 是边界问题（多一个字少一个字，如"科融环境"抽成"万科融环境"）。针对前者试过候选重排（规则 + 词典两版），**都是负收益**（86.1% → 71.7% / 72.1%），因为 26% 的正确答案是词典里没有的新名字，强行替换会把对的改错。

## 5. 工程类

**Q15：4GB 显存怎么塞下的？**

- 答：三件事叠加。①只对答案 token 算 loss：`lm_head` 输出是"序列长度 × 词表 15 万"，fp16 下 seq=512 就是 150MB，这层峰值一叠加就爆；改成只算答案位置省约 600MB。②LoRA 只训 0.84%，优化器状态几乎不占。③序列长度按数据 P99 定（128/512/320），不统一写 512。最终峰值 1.55GB，batch 2 + 梯度累积 4 + 梯度检查点。

**Q16：训练一次多久？能不能更快？**

- 答：情绪 169 分钟、新闻 179 分钟、实体 190 分钟。提速只有三条：降序列长度（已按 P99 压过）、降数据量、换卡。我们试过 batch 16 直接 OOM，batch 4 是稳定上限。

**Q17：怎么保证训练没白跑？**

- 答：三层自检。①训练前 `check_train.py` 检查掩码（prompt 部分 label 是否为 -100）、切分、可训练参数数；②训练中每步检查"拿到梯度的参数 392/392"，不是全中说明有层没挂上；③每 300 步存断点、日志逐行 flush，进程被杀能续。

**Q18：模型怎么部署？adapter 怎么版本管理？**

- 答：三个 adapter 同时挂在同一基座上，按请求切换，每个约 20MB。版本方面，权重走 GitHub Release，代码里用固定路径；如果要上生产，应该把"adapter + 基座 ID + 数据版本 + 评估分数"一起登记，配 canary 和回滚。

## 6. Agent / 外壳类（差异化，容易被深挖）

**Q19：为什么模型外面还要加一层？不是掩盖模型缺陷吗？**

- 答：两层目的。①**格式与合法性**：分类只允许三个标签、实体必须出现在原文，这些是契约，模型没有义务遵守；②**知道自己不会**：0.6B 给一段闲聊也会硬分一个标签，所以要有拒答通道。这不叫掩盖，叫把"不确定"显式化——金融场景里，答错比拒答贵得多。

**Q20：三档阈值怎么定的？**

- 答：不是拍的，是在回归集上算"覆盖率-准确率"曲线。结果三个任务阈值完全不同：情绪 0.90（覆盖 37%、该档 94.3%）、新闻 0.95（覆盖 79%、95.4%）、实体 0.89（覆盖 39%、95.1%）。还有个反直觉发现：情绪任务做不到"95% 准 + 30% 覆盖"同时满足，最高只能到 94.3%。

**Q21：投票 +2pp 值不值 1.66 倍成本？**

- 答：看场景。我们实测 200 条：贪婪 89.0% → 三次投票 91.0%，救回 5 条、坑掉 1 条，只有置信度 <0.88 的 33% 请求触发。批量离线场景值得；在线低延迟场景不值得，可以把触发阈值调到 0.85（只有 8% 触发，收益 +0.5pp）。

## 7. 反思类（准备好，几乎必问）

**Q22：这个项目最大的失败是什么？**

- 答：**五个改动里有三个是负收益**，我提前没算成本就做了。①实体候选重排 86.1%→71.7%；②别名归一化只救回 1 条；③few-shot 改提示词掉了 10 个点。共同点是我在"后处理"和"提示词"上找答案，而真正的问题是标签噪声。现在我会先做错例结构分析，再决定动哪里。

**Q23：如果重来，你会怎么改？**

- 答：顺序反过来。①先跑官方 test 切片，确认对外数字站得住；②再做置信学习去噪（这是唯一有强证据支撑的方向）；③最后才调超参和加外壳功能。

**Q24：通用能力掉了多少？（灾难性遗忘）**

- 答：**没测**，这是明确的缺口。面经里这题的标准答案是"保留一个通用能力的留出集，和任务指标一起看；治理手段是混入 10% 通用数据、降学习率、减轮数、降 rank"。我们的做法是只训 1 轮、低 rank，理论上遗忘较轻，但没有实测数据支撑。

**Q25：给你 8 张 A100 和一周，你做什么？**

- 答：三件。①用 7B 基座做同数据对照，确认"0.6B 够用"是任务特性还是我的错觉；②从更大模型蒸馏软标签（现在没条件，这是最可能突破 86% 的路径）；③把三个任务合并成一个多任务 adapter，省显存但要监控任务干扰。

## 9. 一句话介绍这个项目（30 秒版）

> 在 4GB 消费级显卡上，用 LoRA 微调 Qwen3-0.6B，做了中文金融的三个窄任务：情绪分类、新闻分类、事件主体抽取。三个任务全量评估分别是 76.3%、89.7%、86.1%，其中两项超过了 GPT-4o 在同类公开评测上的零样本成绩。模型之外我做了一层校验和调度，把"不确定"变成显式的三档输出。最大的收获是知道瓶颈在数据不在模型：我试过三种后处理优化，全是负收益。

# 10. 三道必被追问的题：白板推导 + 代码位置

面试官如果只挑三处往深里问，最可能是这三道：**LoRA 为什么省显存、4GB 怎么塞下的、投票值不值**。共同点是都能用算术算出来，算得对就赢一半。

---

## Q4 展开：LoRA 的参数量和显存账

### 白板推导

Qwen3-0.6B 的维度（来自 `config.json`）：hidden 1024、intermediate 3072、28 层、16 个注意力头、8 个 KV 头、head_dim 128。

LoRA 每个模块新增参数 = r × (输入维度 + 输出维度)。我们挂 7 个模块，r=8：

| 模块 | 输入 → 输出 | 参数 |
|---|---|---|
| q_proj | 1024 → 2048 | 8 × 3072 = 24,576 |
| k_proj | 1024 → 1024 | 8 × 2048 = 16,384 |
| v_proj | 1024 → 1024 | 8 × 2048 = 16,384 |
| o_proj | 2048 → 1024 | 8 × 3072 = 24,576 |
| gate_proj | 1024 → 3072 | 8 × 4096 = 32,768 |
| up_proj | 1024 → 3072 | 8 × 4096 = 32,768 |
| down_proj | 3072 → 1024 | 8 × 4096 = 32,768 |

单层合计 180,224，乘 28 层 = **5,046,272**。这和训练日志里打印的 `trainable params: 5,046,272 || all params: 601,096,192 || trainable%: 0.8395` **完全对上**。

显存省在哪，算一遍就清楚：

| 项 | 全参 | 我们的 LoRA |
|---|---|---|
| 权重 | 601M × 2B = 1.2GB | 冻结，只读 |
| 梯度 | 601M × 2B = 1.2GB | 5.05M × 2B ≈ 10MB |
| Adam 两个动量 | 601M × 8B = 4.8GB | 5.05M × 8B ≈ 40MB |
| 合计（不含激活） | **约 7.2GB** | **约 70MB** |

**关键句**：省的不是权重，是**优化器状态**。Adam 对每个可训练参数要存两个 fp32 动量，全参 6 亿参数光这一项就 4.8GB，LoRA 只有 505 万参数，这一项几乎消失。

顺带答两个常见追问：

- **α 为什么是 16**：前向是 `(α/r)·BAx`，α=2r 是让缩放不随 r 漂移的惯例。改 r 不改 α 会隐式改变等效学习率，这是面试官常挖的点。
- **能不能 merge**：能，W = W₀ + BA，merge 后推理零额外延迟。我们没 merge，因为要同时挂三个 adapter 做热切换。

### 代码位置

- `train_sft.py:137-141` —— `LoraConfig(r=lora_r, lora_alpha=2*lora_r, target_modules=LORA_TARGETS[lora_target], ...)`
- `train_sft.py:97` —— `LORA_TARGETS` 两套候选（7 个线性层 / 只挂注意力），注释里写了为什么选 7 个
- `train_sft.py:62` —— 注释记录了这个取舍："target_modules 的选择，是本次对照最关键的一处差异"

### 30 秒怎么讲

> LoRA 冻基座、只学低秩增量。0.6B 上我们挂 7 个线性层、r=8，新增 505 万参数，占 0.84%。省显存的关键不是权重而是优化器状态：Adam 每参数两个 fp32 动量，全参要 4.8GB，我们只要 40MB。加上梯度检查点，峰值压在 1.55GB。

## Q15 展开：4GB 怎么塞下的（只对答案算 loss）

### 白板推导

`lm_head` 的输出形状是 `(batch, 序列长度, 词表大小)`。我们的数：batch 2、序列 512、词表 151,936。

元素数 = 2 × 512 × 151,936 = **1.556 亿**

- fp16 存一份：1.556 亿 × 2B ≈ **311MB**
- 反向传播还要给梯度留一份：再 **311MB**
- cross_entropy 内部会把 logits 升到 fp32：峰值可能再翻一倍

也就是说，这一层单独就能吃掉 0.3~0.9GB，而整张卡只有 4GB。

但真正被监督的只有答案那几个 token：

- 情绪任务答案是"积极。"这类词，**2~3 个 token**
- 实体任务是一整句"所属信批违规事件的金融主体是××。"，约 **18 个 token**

前面几百个位置的 logits 全是白算。所以改成：**先跑 transformer 拿隐状态，只把答案位置的几行送进 lm_head**。

注意一个细节（面试官会问）：预测第 t 个 token 用的是第 t-1 个位置的隐状态，所以切片是 `h[s-1 : e-1]`，不是 `h[s:e]`。我们的实现里就写了这一行。

### 代码位置

- `train_sft.py:456-490` —— `answer_only_loss()`，函数注释里直接写了这段显存账
- `train_sft.py:479-481` —— 关键三行：`idx = (lab != -100).nonzero()`、`s, e = idx[0], idx[-1]+1`、`logits = lm(h[i, s-1:e-1, :]).float()`
- `train_sft.py:241-244` —— prompt 部分填 `-100`，PyTorch 的 cross_entropy 会忽略它
- `train_sft.py:579-582` —— `--fast_loss` 开关：开就走 `answer_only_loss`，关就走 huggingface 的 `model(..., labels=...)`

### 30 秒怎么讲

> lm_head 的输出是"序列长度 × 15 万词表"。batch 2、序列 512 时，光这一层 fp16 就 311MB，加梯度 622MB，4GB 卡直接爆。但被监督的只有答案那 2~18 个 token。所以我把 lm_head 从整段前向里摘出来，只对答案位置做投影，数学上等价，显存省了 0.6GB 左右，峰值降到 1.55GB。

## Q21 展开：投票 +2pp 值不值 1.66 倍成本

### 白板推导

先算成本。三次投票的期望生成次数 = 1（贪婪）+ 2 × 触发比例（因为已经采过一次，只需补 2 次）：

| 触发阈值 | 触发比例 | 期望生成次数 | 实测准确率 |
|---|---|---|---|
| 不投票 | 0% | 1.00× | 89.0% |
| 0.85 | 8% | 1.16× | 89.5% |
| **0.88** | **33%** | **1.66×** | **91.0%** |
| 0.89 | 52% | 2.04× | 91.0% |
| 0.92 | 100% | 3.00× | 91.0% |

这张表说明两件事：

1. **收益在 0.88 就到顶了**，再往下放阈值只增加成本，准确率不再涨
2. 0.88 之前（0.85）只触发 8%，但也只赚 0.5 个点，属于"便宜但没用"

再看收益的稳定性。200 条里：救回 5 条、坑掉 1 条，净 +4 条 = +2.0pp。低置信那 52% 的片段提升更明显：81.9% → 85.7%。

**值不值的判断**（面试官真正想听的）：

- 离线批量、错一条代价高的场景（合规、风控）：1.66 倍算力换 2 个点，值
- 在线低延迟：不值得，把阈值调到 0.85 只多 16% 成本，或者干脆不投票

一个容易忽略的点：**投票后的置信度换了尺度**。贪婪解的置信度是 token 概率的几何平均，投票后是一致度（3 次全中 1.0、2 次 0.67、1 次 0.33）。这两把尺子不能混用，所以判定逻辑必须单独写一套，否则会把答对的样本误判成拒答。

### 代码位置

- `harness.py:48` —— `VOTE_IF_BELOW = 0.88`，注释里写了这张表的结论
- `harness.py:249-268` —— `_generate_vote()`：采样 k 次、抽实体、`Counter(ents).most_common(1)`，返回 `(实体, 一致度, 原始输出)`
- `harness.py:351-355` —— 触发条件：`if conf < VOTE_IF_BELOW:` 才走投票，并置 `voted = True`
- `harness.py:373-380` —— 单独的一套判定规则：一致度 1.0 才可能 auto，0.67 只给 hint，0.33 直接 abstain
- `harness.py:359-360` —— 结果里打 `voted` 标记，日志能追溯哪条走了投票

### 30 秒怎么讲

> 实体任务错例 78% 是"原文有多个公司名挑错了"，我想试试多采几次投票能不能救。200 条实测：贪婪 89.0% → 三次投票 91.0%，救回 5 条坑掉 1 条。成本不是 3 倍，因为我只在置信度低于 0.88 时才补采，触发 33%，平均 1.66 倍。再往下放阈值收益就到顶了，所以我停在 0.88。
